## Local UI

The node serves a status page on your computer at **http://127.0.0.1:7381/** (desktops also get an
"AIs@home node" menu entry). It shows whether the node is connected, paused or
serving, the model, slots in use, the GPU's memory and temperature, requests and tokens
served today and in total (kept across reinstalls), and recent connections and errors. It never shows prompts
or answers. **Your nodes** opens your [account page](https://aisathome.org/account), which shows
each of your nodes' average speed (output tokens a second over its last 50 answers, as the gateway
measured them, waiting and prompt reading included) and what it serves right now: a chat or API
request (never what was asked, or by whom) or a science task, linked to its page.

Pause, Resume, **Restart engine**, **Stop and free the GPU** and **Uninstall…** need the local
password the installer created:

```bash
sudo cat /etc/aisathome-node/ui-password
```

Enter it once and the browser remembers it. **Pause** lets requests in flight finish and
takes no new ones, while the model stays in GPU memory; it lasts until you resume, also
across restarts. To free the GPU, stop the node instead (table above).

**Stop and free the GPU** stops the node and the engine; the page goes away with them, and
`sudo systemctl start aisathome-llama aisathome-node` brings both back. **Uninstall…** asks you to
confirm and has a box to remove the model too. On Windows the page has **Stop engine** and **Start
engine** instead, and no uninstall (Settings → Apps).

When a newer release is out, the page says so ("v0.8.0 is out (you run v0.7.0)"), links to its
notes on GitHub and shows how to update: on Linux the one-line install to copy into a terminal
(`curl -fsSL https://aisathome.org/node.sh | sh`, which updates the installed node and keeps its
settings) and [Update your node](/node/update/); on Windows the
[installer's download](/node/windows/). The page itself installs nothing. To know about new
releases the agent asks the gateway it already connects to (`/v1/node/release`, no token), at most
once an hour and only while the page is open, so the node contacts no other host for it. To turn
the check off, set `AISATHOME_UPDATE_CHECK=off` in the agent's environment: on Linux
`sudo systemctl edit aisathome-node`, then add `[Service]` and
`Environment=AISATHOME_UPDATE_CHECK=off`.

The page is reachable from this computer only. On a machine without a screen, open an SSH
tunnel from your own computer and browse to http://localhost:7381/ there:

```bash
ssh -N -L 7381:127.0.0.1:7381 you@node-machine
```

In a terminal, `aisathome-node status` prints the same; it exits with 0 when the node is
connected and 1 when it is not, so scripts and monitoring can use it.

## Running BOINC on the same GPU

The model takes the whole GPU while it serves, so BOINC's GPU tasks and the node should not
run at the same time. BOINC can step aside by itself whenever the node's engine runs: name
`llama-server` as an exclusive GPU app in `cc_config.xml` in BOINC's data directory
(`/var/lib/boinc-client/` with the Debian and Ubuntu package):

```xml
<cc_config>
  <options>
    <exclusive_gpu_app>llama-server</exclusive_gpu_app>
  </options>
</cc_config>
```

If the file already exists, add only the `<exclusive_gpu_app>` line inside its `<options>`.
Then choose **Options → Read config files** in BOINC Manager, or restart the client
(`sudo systemctl restart boinc-client`).

- BOINC looks at the running processes every 10 seconds. While `llama-server` runs, it
  suspends all its GPU work ("an exclusive app is running"); CPU work goes on.
- The model stays loaded as long as the node runs, also while it is paused in the
  [local UI](#local-ui), so BOINC's GPU work waits all that time. To give the GPU back to
  BOINC, stop the node (**Stop and free the GPU** on its page, or
  `sudo systemctl stop aisathome-node aisathome-llama`): BOINC resumes within about 15 seconds.
- Suspending ends BOINC's running GPU task: it starts again from its last checkpoint, and
  the work since then is lost.
- On Linux BOINC compares only the first 15 characters of a process name; `llama-server`
  fits.
- It has no effect while BOINC's GPU mode is set to **always**; use **based on
  preferences** (BOINC Manager's Activity menu).

## Model check

From release `v0.6.0`, `aisathome-node modelcheck` checks that your engine and model compute
like a published reference. Run it after you update the node or llama.cpp, when you turn
speculative decoding on, or when a new GPU type or driver behaves oddly:

```bash
aisathome-node modelcheck
```

On Windows, in PowerShell: `& "$env:ProgramFiles\AIsAtHome\aisathome-node.exe" modelcheck`.

It sends 100 short prompts to your local `llama-server` (greedy, thinking off, the top 20
token probabilities at each step) and compares the answers with a reference recorded on a known
llama.cpp build, model file and GPU. It takes one to two minutes on a 24 GB card. Nothing leaves
your computer: the prompts are built in, and the references ship inside the program. **Pause**
the node in the [local UI](#local-ui) first, so served requests do not wait behind the check;
resume it afterwards.

What it reports:

- **KL divergence** (how far your token probabilities are from the reference's), per group of
  4 prompts. The limit is **0.0085** for the largest group. Honest nodes on other GPUs and
  llama.cpp builds stay well below it; a different quantisation of the model does not.
- **Confident flips:** your greedy answer picks another token where the reference was sure
  (its first choice led by more than 0.5 nats). At most **2** in 100 prompts. Answers that part
  at near-ties are normal (GPUs round differently) and do not count.

| Exit code | Result | What to do |
|---|---|---|
| 0 | `PASS` | Nothing. Your engine and model compute like the reference. |
| 1 | `FAIL` | The numbers differ more than the limits allow: usually another model file, a broken or unusual llama.cpp build, or a corrupted GPU state. Check the model's SHA-256 (the installer does), restart the engine, and run it again; if it still fails, tell us and send the saved run (below). |
| 2 | `COULD NOT CHECK` | No engine answered at `http://127.0.0.1:8000` (`-server` to change it), no reference for the model it serves, or some prompts got no answer. The message says which. |

The report names the reference and notes what differs from it. A reference recorded on
another llama.cpp build moves the numbers a little: a pass still counts, but a narrow failure on
a newer build than the reference's is not conclusive. Speculative decoding (`--speculation
mtp`) does not need its own reference; it passes the plain one. The standard tier's reference
(16 GB cards) is still provisional.

Options: `-out run.json.gz` saves your run (prompts, answers and token probabilities, plus the
llama.cpp build, model file name and GPU model; no node token or paths) to send to us or to
compare later; `-json` prints the result for scripts; `modelcheck list` shows the built-in
references; `-ref` takes another reference file, or an `https://` address together with its
`-ref-sha256`.

The prompts are public, so this is a check of your own setup, not a way for the network to check
nodes.

**Speculative decoding.** On 24 GB cards the Linux installer turns on MTP by default when the card
has 21,000 MiB free; otherwise the node runs without it, and the install says why. To turn it off,
run the installer with `--speculation off` (it is remembered on updates). See
[model settings](/node/presets/#speculative-decoding-mtp).

## Privacy hardening

These measures make it less likely that prompts end up on disk by accident:

- **No core dumps** (`LimitCORE=0`): a crash dump would contain prompts from memory.
- **No swap** (`MemorySwapMax=0`, needs cgroup v2): prompts are never paged out.
- **A bounded prompt cache in RAM** (`--cache-ram`: half the machine's RAM, at most 16384 MiB).
  It keeps recent conversations warm so an agent's next step does not recompute its whole
  prompt; with no swap it never reaches disk. Override with `CACHE_RAM_MIB`; `0` disables it.
- **No prompt logging:** `llama-server` runs without verbose logging.

They do not make the node confidential: anyone with root on the machine can still read
prompts from RAM or VRAM while they are being served.

## Troubleshooting

**`NVIDIA driver ... is too old for the prebuilt llama-server`.** The bundle is built with
CUDA 12.8 and needs driver 525.60.13 or newer (570.26 or newer for an RTX 50). Update the
driver (Ubuntu: `sudo ubuntu-drivers install`), reboot, and run the installer again. Or
[build llama.cpp yourself](/node/install/#build-it-yourself) for your driver.

**`has compute capability ...; the prebuilt llama-server supports 8.6 8.9 12.0`.** The
bundle is built for the RTX 30, 40 and 50 series only. Build llama.cpp yourself for your
GPU.

**`not enough disk space`.** The model needs 13.1 GB (16 GB cards) or 14.3 GB, plus about 2 GB in `/var/lib`. Free
some space and run the installer again; a started download resumes.

**`model checksum mismatch`.** The downloaded model is not the pinned file (a corrupt
download or a changed mirror). The installer deletes it; run it again to download it again.
If it happens twice, tell us.

**`the prebuilt llama-server cannot run here`.** Your system's C library is older than
glibc 2.35 (for example Ubuntu 20.04). Build llama.cpp yourself.

**`no kernel image is available for execution on the device`.** `llama-server` was built for
another GPU generation. Rebuild with `"-DCMAKE_CUDA_ARCHITECTURES=86;89"` (see
[install](/node/install/#build-it-yourself)).

**CMake: `CMAKE_CUDA_COMPILER-NOTFOUND`.** `nvcc` is not on `PATH`:
`export PATH=/usr/local/cuda/bin:$PATH` and configure again from an empty `build/`.

**`no /dev/nvidia-uvm and no nvidia-modprobe`.** The GPU device nodes are missing and the
helper that creates them is not installed: `sudo apt install nvidia-modprobe`, then start
the services again.

**`llama-server found no GPU and ran on the CPU`** (older installers: `llama-server is running
on the CPU, not the GPU`). CUDA saw no GPU inside the service's sandbox. With installers
before v0.2.0 that happens on NVIDIA driver 545 and newer: the sandbox allowed the GPU only
under the name older drivers use. Download the newest bundle and run its `install.sh` again;
it keeps the downloaded model. The installer stops `llama-server` in this case, so nothing
keeps running on the CPU. If the newest installer still says this while `nvidia-smi` works,
tell us and include the output of `grep nvidia /proc/devices`.

**`... MiB free; the standard tier (UD-Q3_K_XL, 80k context) needs 14300 MiB free`** (or the
big tier, 18,500). A screen or programs use too much of the card's memory for its tier; the
installer does not shrink the context. Close programs that use the GPU (`nvidia-smi` lists
them), or connect the monitor to the motherboard's graphics (integrated GPU), then run the
installer again. On a 16 GB card the desktop and other programs may use about 1.5 GB; a
desktop with a browser often takes 1-2 GB.

**`... is the big tier's model ...; this card is in the standard tier`** (or the other way
round). The file given with `--model` belongs to the other tier. Leave out `--model` and the
installer downloads the right file, or download it with `--download-only <dir> --tier
standard` (16 GB cards) or `--tier big` (24 GB and more).

**`llama-server ran out of GPU memory while loading`.** The same, found when the model
loaded: something took GPU memory after the check. The installer stopped the node; free the
memory and run it again.

**`... writes N tokens/s after a 32000-token prompt; the network needs at least 20`.** The
speed test after the install was too slow, so the installer stopped the node. Cards with
slow memory (RTX 4060 Ti, 5060 Ti) do not reach it. If BOINC GPU tasks, a game or a video ran
during the test, stop them and run the installer again.

**`... is not the network's model`.** `--model` takes only the pinned file. Leave it out and
the installer downloads the right one.

**`llama-server did not become healthy`.** Check `journalctl -u aisathome-llama`.

**The node does not connect.** Check the `gateway_url` in `/etc/aisathome-node/node.json`
and that the machine can reach `api.aisathome.org` on port 443. A rejected token shows up
in `journalctl -u aisathome-node`.

**`watchdog: no word from the gateway`** in `journalctl -u aisathome-node`. The agent pings
the gateway every 15 seconds and reconnects when an answer does not come within 30. If it has
still had no working link after 5 minutes (time paused or with the engine unhealthy does not
count), it exits with an error and systemd starts it again 5 seconds later. Now and then, for
example during a gateway outage, this is harmless; if it repeats, the machine cannot keep a
connection to `api.aisathome.org`. To change the limit or turn it off, add
`Environment=AISATHOME_WATCHDOG=10m` (at least `1m`, or `off`) with
`sudo systemctl edit aisathome-node`.

**After suspend.** The node stops before suspend and starts again after resume. If the GPU
was reset, the watchdog restarts `llama-server` within a few minutes.
